# Camen codebase audit

**Date:** 2026-09-17  
**Baseline:** `4c74b35` — version 1.15.0  
**Scope:** Audit only; no application fixes retained.

## Executive assessment

Camen has a coherent product identity and a small, understandable technology stack. Its primary weaknesses are capture lifecycle coordination, correctness at native-library boundaries, and persistence consistency—not a shortage of features.

The highest-priority findings are missing native source in Git, videos archived with JPEG extensions, overlapping burst/single-shot pipelines, recording startup cancellation, and unbounded image-manipulator retries. These affect reproducibility and reliable capture. Additional deterministic defects affect focus coordinates, zoom calibration, portrait blur, GPS EXIF, manual controls, and the shot browser.

TypeScript passes, the installed dependency tree resolves, and all 10 existing portrait tests pass. Those checks do not cover the identified integration failures.

### Evidence and limitations

- All first-party TypeScript/TSX application files were read across the main review and the completed capture-audit agent. The local Kotlin segmentation implementation, camera patch, test script, and key Android/configuration files were inspected.
- Project intent was checked against README, the master plan, hardware report, and selected detailed chapter/changelog material. Historical documentation was inspected, not treated as proof that behavior still works.
- Tracked files and ignore rules were inventoried. Relevant installed camera, media-library, image-loader/manipulator, and EXIF dependency implementations were inspected.
- This is **not** a claim to have audited every line of `node_modules`, generated build output, binary APKs/assets, or the 46,291-line raw hardware dump. The raw dump contains historical device diagnostics; the curated report supplied the hardware context.
- No new APK build, clean-clone native build, physical-device UI test, image-quality acceptance pass, dependency advisory-database scan, or external penetration test was performed.
- “Confirmed” means established by code or an isolated executable reproduction. It does not mean every issue was reproduced on the Redmi.
- One unintended two-line focus edit was immediately reverted. The final tracked-code diff was checked separately.

## 1. Project goal and actual architecture

**Product:** An offline-first, minimalist camera for the owner's Redmi K80 Pro, with a dark charcoal/brass interface, photo/video capture, photographic recipes, user-saved looks, optional GPS, and an app-owned shot archive. The release channel is a locally signed sideload APK, rather than a backend or store-dependent service.

### Layers

| Layer | Implementation | Responsibility |
|---|---|---|
| Bootstrap | `index.ts`, `App.tsx` | Buffer polyfill, providers, root camera screen |
| UI | `src/components/` | Camera dashboard, controls, adjustment panel, settings, shot browser |
| Preferences | `settings.tsx`, `userPresets.ts`, `presets.ts` | AsyncStorage preferences and recipe data/cache |
| Capture orchestration | `useCamera.ts` | Shutter, timer, steady wait, burst, recording, processing, saving |
| Photo development | `gradePhoto.ts` | Native resize/crop plus JS JPEG decoding, color grading, encoding |
| Portrait | `vision.ts`, `portraitDepth.ts`, `portraitMath.ts`, `modules/camen-vision/` | ML Kit person segmentation plus synthetic background blur/compositing |
| Persistence | `db.ts` and capture helpers | Permanent files, thumbnails, gallery copies, SQLite metadata |
| Native camera integration | `patches/expo-camera+57.0.5.patch` | Android tap metering and custom view props |

**Photo path:** Camera JPEG → optional orientation/crop → tonal development → optional person segmentation/bokeh → optional WebP → permanent archive → GPS attempt → thumbnail → gallery export → database insert.

**Video path:** Native recording → shared archive/save function. Reusing that photo-oriented function is the source of the video-extension defect.

**Important capability distinctions:**

- EV and ISO are photo-development gain/grain controls, not native sensor exposure or ISO control.
- AEB makes three tonal variants from **one exposure**; it does not capture three sensor exposures.
- HDR is a tone look, not multi-frame HDR reconstruction.
- Night is a low-light recipe, not a multi-frame night stack.
- Portrait uses a **person-confidence mask**, not measured scene depth. Its proximity heuristic is synthetic depth of field.
- Preview veils approximate selected looks; they are not the same rendering pipeline used for saved photos.
- Video is ungraded, even while recipe preview overlays remain visible.

These are legitimate scope choices, but the UI and documentation should make them clear.

## 2. High-priority findings

### A01 — P1: Custom Android module source is excluded from Git

**References:** `.gitignore:6`; `modules/camen-vision/expo-module.config.json:4`; `modules/camen-vision/android/build.gradle:1`; `modules/camen-vision/android/src/main/java/expo/modules/camenvision/CamenVisionModule.kt:19`.

The unanchored `android/` ignore pattern excludes **every** directory named Android, including the first-party module implementation. `git ls-files` includes its JS wrapper/config but not its Gradle or Kotlin source. `git check-ignore -v` confirms the exclusion.

**Impact:** This workspace contains native functionality that the committed repository cannot reproduce. A clean checkout lacks the implementation required by the module declaration.

**Recommendation:** Root-anchor generated-project ignores and track the custom module's source while ignoring its build output. Validate native registration from a clean checkout. Do not commit signing material.

### A02 — P1: Recorded videos are archived as `.jpg`

**References:** `src/features/useCamera.ts:428–442`, `src/features/useCamera.ts:868–873`.

The save function chooses only `webp` or `jpg`, regardless of `media.mediaType`. A recorded MP4 is consequently renamed to JPEG.

**Impact:** Video thumbnail detection misses its video branch; Android gallery export classifies by the wrong extension; database media type contradicts the filename. With Location enabled, the video also enters JPEG EXIF processing. MP4 bytes are not necessarily lost, but interoperability is broken.

**Recommendation:** Use an explicit media descriptor for extension, MIME type, thumbnail strategy, and EXIF eligibility. Keep video persistence separate from photo-only processing.

### A03 — P1: Burst capture does not own the capture lock

**References:** `src/features/useCamera.ts:752–785`, `src/features/useCamera.ts:913–927`, `src/features/useCamera.ts:946–955`.

Burst acquisition leaves `phaseRef` at `ready`. Releasing the shutter clears the burst flag while a native capture can still be pending. A quick subsequent tap starts a second capture pipeline.

**Evidence:** The capture audit's controlled-promise harness executed the actual hook and observed two `takePictureAsync` calls before the first resolved.

**Impact:** Overlapping native capture, independent saves resetting shared state, and subsequent bursts interfering with each other's flags.

**Recommendation:** One capture-session owner must cover startup, acquisition, draining, and persistence, including burst release.

### A04 — P1: Stop during video startup does not cancel the pending recording

**References:** `src/features/useCamera.ts:819–850`, `src/features/useCamera.ts:885–900`.

The UI enters recording state before permission checks finish. Stop forwards a native stop without canceling startup; the pending chain later calls `recordAsync` anyway.

**Evidence:** The hook harness observed `stopRecording` followed by `recordAsync`. Installed native code stops only an already-created recording.

**Impact:** A video starts after the user requested Stop. Displayed/saved duration also includes permission/startup delay.

**Recommendation:** Represent `starting` separately, use a cancellation generation/token, and start the duration clock when recording actually begins.

### A05 — P1: Manipulator retry is unlimited and can leave capture permanently busy

**References:** `src/features/gradePhoto.ts:43–60`; `src/features/useCamera.ts:285–301`, `src/features/useCamera.ts:440–445`.

Despite logging “retrying once,” `queuedManipulate` recursively retries every matching `renderAsync`/`Context.` error without a limit. Crop and thumbnail waits are outside the develop watchdog.

**Impact:** A persistent native failure can keep the shutter in capturing/saving indefinitely; a supposedly optional thumbnail can block database insertion.

**Recommendation:** Explicit bounded retry count, narrow transient-error classification, and a settling deadline at the session boundary. Rotation and WebP conversion also bypass the shared queue (`useCamera.ts:270`, `useCamera.ts:398`), undermining its single-entry-point guarantee.

## 3. Functional and data correctness

### A06 — P2: Focus coordinates subtract the frame offset twice

**References:** `src/components/CameraScreen.tsx:128–138`, `src/components/CameraScreen.tsx:290–302`.

The tap detector is attached to the framed child view, so `e.x/e.y` are local. The handler subtracts `frame.x/frame.y` again.

**Evidence:** Using the actual expressions and framing helper on a 400×800 surface: square center maps to `(0.5, 0)` rather than `(0.5, 0.5)`; Instagram center maps to `(0.5, 0.2)`; Wide center has a negative Y and is rejected.

**Recommendation:** Normalize local coordinates directly. Test nonzero horizontal and vertical frame offsets, not only Full framing.

### A07 — P2: Zoom labels do not match the installed native zoom mapping

**References:** `src/features/deviceProfile.tsx:80–90`; `src/components/CameraScreen.tsx:239`; installed `node_modules/expo-camera/android/src/main/java/expo/modules/camera/ExpoCameraView.kt:674–677`.

The JS mapping assumes normalized zoom interpolates across 0.6–10. Installed Android instead uses `max(1, min(nativeMax, normalized * nativeMax))`.

**Impact:** “0.6×” produces at least native 1×, not ultrawide. With native max 10, labeled 2.5× requests approximately 2.02×. Targeting one known phone does not correct this incompatible API mapping.

**Recommendation:** Align the adapter with the actual native contract, including support for minimum ratios below 1. Verify the lens/field of view on the phone before retaining ultrawide labels.

### A08 — P2: Portrait near/far weighting is reversed

**References:** `src/features/portraitMath.ts:123–130`, `src/features/portraitMath.ts:238–243`.

Proximity is documented and constructed as high near the subject and low far away. The composite selects `near * (1 - proximity) + far * proximity`, the reverse of that definition.

**Evidence:** A two-pixel synthetic composite with near-band value 40 and far-band value 200 outputs 40 far from the subject and 200 near it. All existing portrait tests still pass.

**Recommendation:** Correct the blend direction and add explicit endpoint tests. Separately, blur bands include subject pixels; silhouette color bleeding is an image-quality concern requiring visual tests, not a measured device finding here.

### A09 — P2: GPS EXIF rationals have an extra nesting level

**References:** `src/features/geotag.ts:20–40`.

`toDms` returns `[[[degrees,1],[minutes,1],[seconds,100]]]`; piexif expects `[[degrees,1],[minutes,1],[seconds,100]]`.

**Evidence:** The capture audit executed this source with the installed encoder: injection completed, but reading latitude/longitude returned invalid `[0,0]` rationals. SQLite coordinates remain correct.

**Recommendation:** Use the correct rational-array shape and round-trip positive/negative fractional coordinates through the real EXIF library.

### A10 — P2: RESET merges instead of replacing the recipe

**References:** `src/components/DevelopPanel.tsx:161–165`; `src/components/CameraScreen.tsx:736`; `src/features/presets.ts:25–30`.

RESET emits the selected recipe as a partial update; its parent merges it with current values. Fields absent from the recipe survive. Standard's empty recipe therefore resets nothing.

**Evidence:** Resetting Standard from `{bw:true, grain:0.5}` retains both values.

**Recommendation:** Separate recipe replacement from individual field updates.

### A11 — P2: ADJUST displays wrong neutral values for saturation and skin

**References:** `src/components/DevelopPanel.tsx:194–208`; `src/features/gradePhoto.ts:112–113`, `src/features/gradePhoto.ts:563–564`.

The panel defaults every missing numeric field to zero. Saturation and orange/skin saturation default to **one** in the processor. Standard therefore displays 0% while the saved output uses 100%; the Skin slider's default is also outside its 0.7–1.1 range.

**Recommendation:** Share semantic defaults between rendering, editing, equality checks, and processing.

### A12 — P2: Grain also introduces systematic darkening

**Reference:** `src/features/gradePhoto.ts:332–338`.

`Math.sin(...) - 0.5` has a negative mean, not a zero-centered noise distribution.

**Evidence:** Grading a neutral 256×256 image with grain 1 and no other adjustment moves mean intensity from 128 to approximately **112.68**.

**Recommendation:** Use zero-mean noise and test exposure neutrality independently of texture strength. An intentional darkening should be an explicit exposure/tone parameter.

### A13 — P2: Delete promises gallery removal but does not remove the export

**Reference:** `src/components/ShotsScreen.tsx:52–65`.

The confirmation says “from Camen and the gallery,” but the implementation deletes only local archive/thumb files and the SQLite row. It never deletes the gallery asset. File deletions are also launched without awaiting success, while the row is removed immediately.

**Impact:** Sensitive images can remain in the gallery after apparent deletion; failed local deletion can leave unindexed files.

**Recommendation:** Clearly distinguish deleting the archive copy from deleting the export, and await/handle each operation before reporting success. Retain appropriate gallery identifiers if synchronized deletion is desired.

### A14 — P2: Shots older than the latest 200 are inaccessible through the browser

**References:** `src/components/ShotsScreen.tsx:45–50`, `src/components/ShotsScreen.tsx:121–151`; `src/data/db.ts:154–165`.

Each tab loads only 200 rows, with no pagination or load-more handler. The header counts all rows, and older files remain on disk.

**Recommendation:** Add stable cursor pagination. This is hidden history, not deletion of the old files.

### A15 — P2: WebP sharing claims JPEG MIME type

**Reference:** `src/components/ShotsScreen.tsx:186–191`.

Every non-video share uses `image/jpeg`, including genuine `.webp` outputs.

**Recommendation:** Persist or derive the actual MIME type consistently with saving and sharing.

### A16 — P2: Front flash remains white throughout development and saving

**References:** `src/features/useCamera.ts:606–621`, `src/features/useCamera.ts:634–669`; `src/components/CameraScreen.tsx:756–764`.

The white overlay is cleared only after GPS, development, AEB, thumbnails, export, and database insertion finish—not after exposure.

**Recommendation:** End illumination immediately after native photo acquisition, with restoration guaranteed on failure. Keep development state visually separate from flash illumination.

### A17 — P2: Lens/mode changes are not consistently excluded during pending photos

**References:** `src/features/useCamera.ts:593–626`, `src/features/useCamera.ts:740–749`; `src/components/CameraScreen.tsx:399–433`.

Lens switching blocks only recording. Switching during steady wait lets the suspended closure capture from the new camera while carrying the previous facing/flash metadata. Switching to VIDEO during a photo countdown leaves its timer armed; expiry still invokes photo capture against video mode.

**Recommendation:** Define legal mode/lens transitions centrally and cancel or reject pending operations consistently.

### A18 — P2: Anti-shake's timeout depends on continuing sensor events

**Reference:** `src/features/useCamera.ts:549–589`.

The four-second expiry is evaluated inside the accelerometer callback, not an independent timer. If sensor delivery stops, the promise does not reach its advertised deadline. The subscription/wait also lacks corresponding unmount cleanup.

**Recommendation:** Independent deadline plus common completion/cleanup logic. Actual Redmi background sensor delivery was not tested.

### A19 — P2: Files and SQLite can become permanently inconsistent

**References:** `src/features/useCamera.ts:431–479`, `src/features/useCamera.ts:650–663`; `src/data/db.ts:147–165`.

Archive movement and gallery export happen before row insertion. A database write failure leaves a permanent file that the DB-only browser cannot discover. There is no reconciliation journal or scan. AEB save iteration also aborts the remaining variants on the first save failure.

**Recommendation:** Model saves as recoverable operations with explicit states; reconcile archive/index discrepancies and isolate per-variant errors. Do not treat a multi-resource save as an atomic operation when it is not.

### A20 — P2: Development intermediates are not fully reclaimed

**References:** `src/features/gradePhoto.ts:524–535`, `src/features/gradePhoto.ts:581–591`; `src/features/useCamera.ts:650–663`.

The temporary JPEG created for the 2560px resize is neither deleted inside `developPhoto` nor returned in its cleanup metadata. Repeated high-resolution developed captures accumulate these cache files; AEB creates more.

**Recommendation:** Each stage should own and reclaim its intermediates in `finally`, or transfer explicit ownership to the caller. This concerns cache accumulation, not proof of permanent storage exhaustion.

## 4. Lower-priority and hardening findings

### A21 — P3: Countdown arc mixes seconds and milliseconds

**References:** `src/features/useCamera.ts:714–717`, `src/features/useCamera.ts:733`; `src/components/CountdownRing.tsx:22–23`.

`remaining` is seconds while `total` is milliseconds. A ten-second countdown starts at 0.001 progress rather than 1. The numeral is independent and can still be correct.

### A22 — P3: Resolution promises are inconsistent with processing

**References:** `src/components/SettingsScreen.tsx:83–110`; `src/features/framings.ts:55–72`; `src/features/gradePhoto.ts:7–8`.

Settings says “no downscaling” and displays dimensions derived from static landscape sensor bounds. Developed photos are capped at 2560px; WeChat has its own cap. `cropDims` also returns fractional dimensions for some aspects, unlike rounded pixel crops in `cropToAspect`.

**Recommendation:** Label dimensions as estimates or calculate the actual oriented crop/develop output; remove the blanket no-downscaling promise.

### A23 — P3: Persistence accepts structurally invalid data and hides failures

**References:** `src/features/settings.tsx:101–123`, `src/features/settings.tsx:141–143`; `src/features/userPresets.ts:27–51`; `src/components/CameraScreen.tsx:694–741`.

JSON parsing is cast to the expected shape without runtime validation. Valid JSON such as `develop:null` or a non-array user-preset payload can later crash consumers. Settings write failures are swallowed; user-preset mutation promises have no UI error handling. Concurrent preset mutations also use uncoordinated read-modify-write operations.

**Recommendation:** Validate/migrate persisted shapes, serialize mutations, and expose write failure. These are local integrity/reliability issues, not a demonstrated remote attack path.

### A24 — P3: Database initialization assumes every migration failure means “already exists”

**References:** `src/data/db.ts:41–103`.

Every `ALTER TABLE` exception is swallowed, including real I/O/schema failures. Initial database opening/schema creation happen at module import with no recovery UI. The comment says WAL, but this file never enables WAL; the actual runtime journal mode was not measured.

**Recommendation:** Version migrations, verify existing columns, propagate unexpected errors, and provide recoverable startup error handling. The present INSERT has **26 columns, placeholders, and bound values**; the historical placeholder-count defect is not present.

## 5. Hardcoding assessment

### Intentional and reasonable

- Owner attribution and X URL: explicitly part of the product requirement.
- Redmi device identity and baseline capabilities: deliberate single-device scope.
- Theme palette, spacing, photographic recipe coefficients, aperture stops, framing ratios.
- A 2560px processing cap, 512px portrait work grid, recording duration cap, and burst limits are legitimate budgets. They need documentation/tests, not automatic removal.

### Incorrect or fragile

- **Zoom conversion assumptions:** disagree with the installed native implementation (A07).
- **Media extension/MIME choices:** hardcode photo behavior into video and WebP paths (A02/A15).
- **All-fields-zero UI defaults:** disagree with processor defaults (A11).
- **200-row archive ceiling:** silently hides older records (A14).
- **Fixed popover offsets** (`CameraScreen.tsx:661`, `DevelopPanel.tsx:262`): approximate rather than measure the trigger position. Keyboard/safe-area/layout overlap requires device validation; no screenshot failure is claimed.
- **Local release configuration:** Android versionCode 15, NDK pin, and release signing configuration live in ignored Gradle files; app.json does not preserve all these settings. Regeneration/clean checkout is not a reproducible release configuration. Password literals were observed in the ignored signing block; their values are deliberately omitted here, and no committed credential leak is claimed.
- **Native decode budget:** `MAX_DECODE_EDGE = 768`, but the loop compares against `MAX_DECODE_EDGE * 2` (`CamenVisionModule.kt:79–80`). The stated ≤768 cap is not enforced; a 2560px edge can decode at 1280px. The `rawSizeMask` argument is ignored because raw masks are always enabled.

## 6. Ecosystem and maintainability

### What is working well

- A single-screen app does not need a router or global state framework merely for appearances.
- Domain separation already exists for presets, framing math, portrait math, database access, and visual primitives.
- Recipes are data-driven and the custom module is lazily loaded with a graceful missing-module fallback.
- SQL uses bound values for shot insertion/query/deletion. Constant column declarations in migrations are not user-input SQL injection.
- The archive is independent of gallery read permission, a useful offline-first boundary.
- Installed `expo-camera@57.0.5` matches the custom patch; reverse dry-run patch verification passes.
- Dependency installation includes `react-native-worklets`, and the top-level dependency tree has no reported missing/invalid packages.

### Structural weaknesses

1. **The largest modules own too many responsibilities.** `CameraScreen.tsx` is 1,049 lines and `useCamera.ts` 1,007. The hook mixes hardware lifecycle, orchestration, image processing, permissions, storage, metadata, and UI notifications. The important refactor boundary is an explicit capture session plus a media repository—not arbitrary splitting by line count.
2. **Processing runs synchronously on the JS thread.** JPEG decode/encode, grading, base64 conversion, and portrait compositing do substantial work there. A Promise timeout cannot interrupt a synchronous loop while it owns the thread. Exact device latency/memory use was not benchmarked.
3. **Timeouts do not cancel losing jobs.** `Promise.race` fallbacks can leave native/async work running; eventual outputs can be orphaned. Ownership and cancellation matter more than adding another timeout.
4. **Weak boundary types hide real errors.** Broad `Record<string,unknown>` EXIF declarations let the GPS shape error compile. Settings and native-mask results lack shape/length validation.
5. **Some direct imports depend on transitive installation.** `expo-file-system` and `expo-modules-core` are imported by first-party code but are not declared directly in package.json. They currently resolve; explicit dependency intent would make upgrades safer.
6. **Permission/navigation recovery is incomplete.** Camera denial only offers another request, not a `canAskAgain`-aware Settings route. Settings/SHOTS are absolute views without app-level Android Back handling. These paths need device usability tests.
7. **Accessibility state is sparse.** Several visually toggled controls expose button labels but not selected/checked/value state. Rulers do not expose semantic adjustable actions. Labels alone do not make the full camera workflow accessible.

### Documentation drift

README still advertises the removed filter carousel and an old v1.9.0 install artifact. It recommends Expo Go without explaining that current native focus/segmentation behavior needs a custom build. Older plan chapters describe removed picture-size controls or superseded GPU work; these should remain historical, not current specifications.

The current native portrait feature and skin smoothing supersede older “tonal only/no smoothing” text. Update the current product description instead of treating every historical spec contradiction as a new code defect.

### Privacy/security posture

The reviewed app is local-first, with explicit sharing and optional location. No backend or authentication architecture is evident in first-party source. This is not an attestation that the complete dependency graph has no network behavior.

The local Android manifest includes broad declarations such as READ_MEDIA_AUDIO, SYSTEM_ALERT_WINDOW, and WRITE_SETTINGS beyond obvious app needs, and allows backup. Review the final merged release manifest and backup policy for private photos/GPS. A declaration is **not** evidence that the user granted or the app exercised the permission.

Release logs include GPS coordinates (`useCamera.ts:433`). Consider redaction or opt-in diagnostic logging. No exploit development or offensive testing was performed.

## Conclusion

Camen's product direction and library choices are viable. Reliability is limited by mismatched contracts and loosely coordinated asynchronous operations. The most valuable corrections are reproducible native source, media-aware persistence, and a single capture-session lifecycle, followed by the deterministic focus/zoom/portrait/EXIF/control defects documented above. This report is an assessment; no fixes, release build, commit, push, or publication were performed.
